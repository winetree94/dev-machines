# Instructional Context - ansible-for-dev

This project is an Ansible-based automation suite that bootstraps and configures development machines. Supported targets: Ubuntu 24.04+, macOS (Homebrew), and Windows 10/11 (winget over OpenSSH). It supports both localhost and multiple remote hosts.

## Project Overview

- **Purpose:** Automate the installation and configuration of developer tools, CLI utilities, and GUI applications.
- **Main Technologies:**
  - **Ansible:** Orchestration and configuration management.
  - **Package Managers:** APT/Snap/Flatpak (Ubuntu), Homebrew (macOS/Linux), winget (Windows).
  - **Key Tools Managed:** Docker, Mise (runtime manager), Neovim, Kubernetes (kubectl), Zsh, Tmux, Git, and various AI CLI tools.
- **Architecture:**
  - **Playbooks:** Entry point is `playbooks/setup.yml`, a multi-play playbook (`playbooks/ping.yml` is a connectivity check split by OS):
    1. `Group hosts by OS` — an `assert` fails the host up front unless it is Windows, macOS or `distribution == 'Ubuntu'` (the `group_by` below funnels every other Linux into `ubuntu`, so an unsupported distro has to be rejected before any role runs); `group_by` then assigns each host to `ubuntu` / `macos` / `windows` at runtime from facts, so `localhost` works on any supported control machine.
    2. `Ubuntu bootstrap` — apt_update, snap, flatpak, homebrew deps + GUI auto-detection (xsessions/wayland, WSL excluded).
    3. `MacOS bootstrap` — xcode (Command Line Tools headlessly via softwareupdate, then Xcode.app via `mas`).
    4. `Windows bootstrap` — winget with no packages (assert only; winget ships with the OS).
    5. `Group GUI-enabled hosts` — `group_by` puts every host with `gui` true into `gui_enabled`. It cannot be folded into play 1: on Ubuntu `gui` is only final after the desktop detection in play 2.
    6. `Common tooling` — all cross-OS roles, including the four AI CLI roles.
    7. `GUI applications` — `hosts: gui_enabled`, one role per desktop application. Skipped entirely when no host has `gui`.
  - **Roles:** Modular logic under `roles/`. Each role's `tasks/main.yml` is a `first_found` dispatcher including `debian.yml` / `darwin.yml` / `windows.yml`. Missing file = no-op for that OS, and that absence is how per-OS curation is expressed. `default.yml` is still a dispatcher target but no role uses one any more (see below).
  - **Inventories:** `inventories/hosts.yml` holds connection identity only, for four machines: `desktop` (windows), `ubuntu-dev` (ubuntu), `macmini` (macos) and `localhost`. Remote hosts sit in a static OS group so connection vars from `inventories/group_vars/<group>.yml` apply before connecting; `localhost` is deliberately ungrouped and classified at runtime, because the control machine may be macOS or Ubuntu. It can never be Windows: ansible-core does not run as a control node on native Windows, and under WSL `localhost` is the WSL Linux guest — the Windows side is managed as the remote `desktop` host over SSH. Per-host overrides go in `inventories/host_vars/`.
  - **Group Vars:**
    - `all/main.yml` — plaintext: `gui` default and the `ansible_private_key` vault indirection.
    - `all/vault.yml` — the single ansible-vault encrypted file; `vault_*` variables only.
    - `ubuntu.yml` — `ansible_become_method: sudo_wrapped` (custom plugin in `plugins/become/`), `gui: false` (auto-detected).
    - `macos.yml` — `ansible_become_method: sudo`, `gui: true`.
    - `windows.yml` — SSH + `ansible_shell_type: powershell`, `ansible_become_method: runas`, `gui: true`. WinRM alternative documented inline.

## Key Commands

```bash
make install-tools          # yamllint, ansible-lint (pipx)
make install-requirements   # ansible-galaxy collections (requirements.yml)
make verify                 # syntax check + tests/validate_*.yml + yamllint + ansible-lint
make ping                   # ansible-playbook ./playbooks/ping.yml (win_ping on Windows)
make check                  # ansible-playbook --check --diff
make apply                  # ansible-playbook ./playbooks/setup.yml
```

Every target passes `$(ANSIBLE_ARGS)` through, which is how scope is narrowed:
`make check ANSIBLE_ARGS="--limit macmini"`. Without `--limit` these now target all four machines.

Requires `.vault_pass` with the vault decryption password - that one file is the only
secret setup step, since the SSH private key is in the vault too.

### Configuration Options

- **GUI Apps:** auto-enabled when a desktop environment is detected on Ubuntu (WSL excluded); always enabled on macOS/Windows. Override with `-e "gui=true|false"` or `inventories/host_vars/<host>.yml`.
- **`gui` consumers:** the `GUI applications` play (via the `gui_enabled` group built by the `Group GUI-enabled hosts` play) and the Linux systray tasks in `roles/tailscale/tasks/debian.yml`.

## Development Conventions

- **Role Structure:** dispatcher `tasks/main.yml` + OS files (`debian.yml`, `darwin.yml`, `windows.yml`). Never put OS `when:` conditions inline in shared roles; OS-exclusive roles (`apt_update`, `snap`, `flatpak`, `homebrew`, `xcode`, `winget`) are gated by play targeting in `setup.yml` instead.
- **Homebrew on Linux:** most CLI roles (`mise`, `opencode`, `kubectl`, `ripgrep`, …) use Homebrew on Linux as well as macOS, because nearly every one of these formulae ships a Linux bottle. When `debian.yml` and `darwin.yml` would be identical, share a `brew.yml` sub-file included from both, the way `roles/neovim`, `roles/opencode` and `roles/flux` do - never a `default.yml` (see below). A single-formula role is short enough that duplicating two lines across the two OS files beats a sub-file.
- **Windows packages:** every Windows install goes through the shared `winget` role - `include_role: winget` with a `winget_packages` list of winget IDs. Never call a package manager module directly in a `windows.yml`. Chocolatey and Scoop were both retired: choco only tracks installs it made itself and dies with a generic MSI 1603 when it tries to lay a package over an install it did not make (measured on `desktop` for tailscale, docker-desktop and python3), while Scoop does not register in Add/Remove Programs so winget cannot see what it installed. winget decides installed-state from Add/Remove Programs, so it recognises software installed by any means. Idempotency is one exit code: `winget list --id <id> --exact` returns 0 when installed and -1978335212 (`0x8A150014`) when not. Always pin `--source winget`; the msstore source needs separate agreement handling and returns IDs that cannot be automated. winget itself ships with Windows 10 1809+/11, so there is nothing to bootstrap: the role's own availability assert covers it, and the `Windows bootstrap` play includes the role with no packages (`winget_packages` defaults to `[]`) to run just that assert. The check is gated on a `winget_available` fact so it costs one WinRM round trip per host rather than one per including role.
- **Pinned winget IDs:** winget has no floating Python ID, so `roles/python/tasks/windows.yml` pins `Python.Python.3.14` and has to be bumped by hand each minor release. This is the one thing Chocolatey's `python3` meta-package did better.
- **Xcode:** `xcode` runs in the `MacOS bootstrap` play, before `Common tooling`, because the Command Line Tools are the prerequisite for Homebrew and for every role that compiles anything. It never calls `xcode-select --install`: that opens a GUI dialog and returns immediately, so over SSH nobody clicks it and the run continues without the tools. Instead it creates the sentinel file the GUI installer itself creates, `/tmp/.com.apple.dt.CommandLineTools.installondemand.in-progress` - `softwareupdate --list` only offers the Command Line Tools while that file exists - installs the newest offered label with `softwareupdate --install`, and deletes the sentinel in an `always:` block, since a leftover sentinel keeps every later `softwareupdate --list` on the host advertising the package. The label is parsed off the bulleted line only (`^\s*\*.*Command Line Tools`); the indented `Title: ... Size: ...` line right below it repeats the name and must not be matched. One regex strips the bullet and the optional `Label:` so both the 10.15+ (`* Label: Command Line Tools for Xcode-16.2`) and the older (`* Command Line Tools (macOS ...) for Xcode-10.1`) formats parse. Xcode.app itself is Mac App Store id `497799835` through `community.general.mas`, same `become: true` + `block`/`rescue` shape as WireGuard, so a host with no Apple ID signed in still finishes the bootstrap with working Command Line Tools. The follow-up configuration is gated on a `stat` of `/Applications/Xcode.app/Contents/Developer` rather than on the mas task, so a host that already had Xcode still gets configured when mas errored: `xcode-select --switch` (only when the active path differs), `xcodebuild -license accept` (gated on `xcodebuild -version` exiting non-zero, which is what an unaccepted licence looks like) and `xcodebuild -runFirstLaunch` (gated on `xcodebuild -checkFirstLaunchStatus`). Signing in to the App Store stays a manual step; no Apple ID credential enters the repository or the vault.
- **One role per application:** every installable thing is its own role. `ai` and `gui_apps` used to bundle 4 and 20 applications into a single task file, which hid the fact that `gui_apps` was a silent no-op on macOS and Windows and that `ai` installed nothing at all on Windows. A bundle also makes adding or dropping one application a diff against a shared file. The 24 roles that replaced them (`claude_code`, `codex`, `copilot_cli`, `opencode` plus 20 desktop applications) are validated together by `tests/validate_app_roles.yml`.
- **No `default.yml`, anywhere:** `default.yml` is the dispatcher's fallback on *every* OS, Windows included, so a role that has one and no `windows.yml` runs Homebrew tasks on Windows. Give each supported OS its own file and let the missing file be the no-op. **No role in the repository has a `default.yml` any more** and `tests/validate_app_roles.yml` sweeps `roles/**/default.yml` to keep it that way, as well as asserting the presence and the absence of each OS file per role. This also retired the debug stubs `roles/ai` and `roles/graphite` used to carry: a stub only existed to stop the dispatcher falling back to a Homebrew `default.yml`, and with no `default.yml` a missing `windows.yml` is already the no-op.
- **Install path priority:** on **Ubuntu**, Homebrew *formula* > Flathub > snap > apt > vendor install script; never add a third-party APT repository for a new application. Homebrew **casks are macOS-only**, so a cask is never an Ubuntu option - of the 24 applications here only `opencode` has a formula that works on Linux. On **macOS**, homebrew-core/cask > vendor tap (tapped with `trust: true`) > `mas`. On **Windows**, the shared `winget` role only; if winget has no package, the application is simply not managed there.
- **AI CLI roles:** `claude_code`, `codex` and `copilot_cli` are Homebrew *casks* on macOS, so Ubuntu runs the vendor installer instead - `get_url` to fetch it and a separate `command` to run it, guarded by a `stat` of `~/.local/bin/<tool>`, never a `curl | bash` pipe. Anthropic publishes an APT repository too; it is deliberately not used. `opencode` is the exception that is a real formula: it comes from `anomalyco/tap` (renamed from `sst/tap`) on both Ubuntu and macOS through a shared `brew.yml`, tapped with `trust: true`, with the token kept fully qualified because homebrew-core now ships a formula of the same name that lags behind. Windows IDs are `Anthropic.ClaudeCode`, `OpenAI.Codex`, `GitHub.Copilot` (**not** `GitHub.CopilotCLI`, which does not exist) and `SST.opencode` (still published under the old `SST` publisher).
- **GUI application roles:** 20 roles, Flathub on Ubuntu, a homebrew-cask token on macOS, a winget ID on Windows. Four are Linux-only projects with no macOS or Windows package at all (`bottles`, `flatseal`, `xclicker`, `remmina`) - do not substitute a different application for them. `parsec` is the only pkg-based cask, so it is the only one passing `sudo_password`. **Microsoft Edge is deliberately not installed on Windows:** the winget manifest ships the Edge Enterprise MSI (`InstallerType: wix`, machine scope) while Windows 11 preinstalls the consumer build, so a version mismatch fails with "the install technology is different from the current version installed" ([winget-cli#4159](https://github.com/microsoft/winget-cli/issues/4159)), and Edge self-updates so winget's recorded version drifts forever. Two IDs are counter-intuitive and were verified against the manifests: `Pinta.Pinta` (not `PintaProject.Pinta`) and `RedisInsight.RedisInsight` (not `Redis.RedisInsight`; `Redis.Redis` is an unrelated ancient Redis server). The macOS cask token is `redis-insight`, hyphenated.
- **One role per application (second pass):** `kubernetes`, `node`, `neovim`, `git` and `zsh` were bundles too, and were split the same way `ai` and `gui_apps` had been. `kubernetes` became `kubectl` / `helm` / `k9s` / `flux` / `kubeseal` / `kubectl_cnpg` / `talosctl` / `talhelper` / `age` / `sops` - note `age` and `sops` are general-purpose encryption tools that were never Kubernetes-specific. `node` became `bun` / `pnpm` / `deno` / `biome` and the role is gone: it never installed Node.js, which `mise` manages. `neovim` kept `lua`, `luarocks` and `tree-sitter-cli` (its own runtime dependencies) and gave up `lazygit` / `ripgrep` / `fd`. `git` kept git and gave up `gh` / `delta`. `zsh` kept the login-shell assignment and gave up `direnv` / `fzf`. Splitting exposed the gaps it was meant to: `kubernetes` installed 10 tools on Unix but only 3 on Windows (`flux`, `talosctl`, `talhelper` and `age` all have winget packages and now get installed), and `git` never installed git at all on macOS or Ubuntu.
- **Ubuntu's apt exceptions:** everything else follows Homebrew-formula-first, but three roles use apt on purpose. `roles/git/tasks/debian.yml`, because Homebrew's own bootstrap needs git before brew can install anything - `roles/homebrew` apt-installs it as a prerequisite - so managing git with brew would be circular. `roles/cmake` and `roles/ninja`, because Homebrew is on CMake 4.x, which removed support for `cmake_minimum_required(VERSION < 3.5)` and fails to configure older projects outright, while noble's 3.28 builds them unchanged; a project that needs the newer CMake can still pass `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`, so the older package is the safer default. ninja follows cmake so the pair stays on one side of the split, and its apt package is `ninja-build`, not `ninja`. macOS and Windows have no equally old package to pick, so both are on 4.x there. (`roles/tmux/tasks/debian.yml` also installs from apt, with no reason recorded.)
- **The shared `mas` role:** `roles/mas` installs the `mas` formula and is included from a `darwin.yml` with `include_role`, the same contract as the shared `winget` role. `xcode` and `wireguard` both need it and used to install it separately. mas is a macOS-only formula with no Linux bottle, so the role has no OS dispatcher - it is gated by its callers. A `mas_installed` fact memoises it, so any number of includes cost one brew call per host.
- **Tools with no winget package** are simply not managed on Windows, and the role has no `windows.yml`: `sops` (winget only has the abandoned `Mozilla.SOPS` 3.7.3 - the project moved to getsops, which has no winget publisher, while Homebrew is on 3.13.3), `kubeseal`, `kubectl_cnpg`, `graphite`, and the Linux-only desktop apps. Counter-intuitive winget ids verified against the manifests: `Sidero.talosctl` (not `SideroLabs`), `talhelper.talhelper`, `GitHub.cli` (lowercase), `BurntSushi.ripgrep.MSVC`. The Homebrew formula for kubectl is `kubernetes-cli` (`kubectl` is only an alias) and for delta it is `git-delta`.
- **Tailscale:** a normal dispatcher role - APT repo + `tailscaled` + GUI-gated systray autostart on Debian, the `tailscale-app` Homebrew cask plus a `/usr/local/bin/tailscale` exec wrapper on macOS, and `Tailscale.Tailscale` through the shared winget role on Windows. The macOS CLI must be a wrapper, not a symlink: the binary resolves its own bundle from the path it is executed as and aborts with "The current bundleIdentifier is unknown to the registry". It never runs `tailscale up`; authenticating each machine stays a manual step.
- **WireGuard:** a normal dispatcher role that installs only - `wireguard-tools` from apt on Debian, the `wireguard-tools` formula plus the Mac App Store GUI client (id `1451685025`) via `community.general.mas` on macOS (there is no Homebrew cask for it), and `WireGuard.WireGuard` through the shared winget role on Windows. The mas task runs with `become: true` - `mas install` refuses to run unprivileged - and sits in a `block`/`rescue` because it still fails when no Apple ID is signed in. Tunnel config and private keys are never deployed by the role and never enter the vault.
- **Doppler:** a normal dispatcher role, one native install path per OS - the official APT repository on Debian, the `dopplerhq/doppler` Homebrew tap on macOS, `Doppler.doppler` through the shared winget role on Windows (Chocolatey has no Doppler package at all). Two macOS gotchas are load-bearing: the tap must be tapped with `trust: true` (Homebrew 6 refuses to load anything from an untrusted third-party tap), and the cask token must stay fully qualified as `dopplerhq/doppler/doppler`, because the bare `doppler` token resolves to homebrew-cask's unrelated `doppler-app`. That rules out `community.general.homebrew_cask`, whose installed-check runs `brew list --cask <name>` and fails on a qualified token, so the install is a `brew install --cask` gated on `brew info --json=v2`.
- **State snapshots, not per-package queries:** every package manager here answers "is it already installed?" from **one snapshot per host**, cached in a fact, and the roles gate on that fact. The cost of a run is remote round trips, not the package manager: on the Windows host an empty command takes 1.82s and `winget list --id X --exact --source winget` takes 2.40s, so 49 roles asking individually spent ~118s of a 330s run. `roles/winget/tasks/snapshot.yml` (`winget_installed_ids`, via `winget export` - `winget list` truncates its Id column to the console width), `roles/brew` (`brew_installed_formulae` / `brew_installed_casks`) and `roles/flatpak` (`flatpak_installed_ids`) publish the facts; consumers gate with `when: "'<token>' not in (<fact> | default([]))"`. The `default([])` is load-bearing: it makes the role fall back to its own module call when the snapshot did not run (a `--tags` invocation, a host without Homebrew), so a missing snapshot is only slower, never wrong. Same shape as the older `winget_available` / `mas_installed` one-shot facts. Do **not** try to make the per-package command cheaper instead - dropping `--source winget` makes it *slower* (3.13s), because winget then also queries msstore. `tests/validate_state_snapshots.yml` fails if a new role calls `homebrew` / `homebrew_cask` / `flatpak` without gating.
- **Tags:** every `- role:` entry in `playbooks/setup.yml` carries a tag of the same name, so `make apply ANSIBLE_ARGS="--tags docker"` runs one role in seconds instead of waiting out a full pass (`ANSIBLE_ARGS` already threads through every Makefile target). Three things must keep `tags: always` or a filtered run silently does nothing: the `Group hosts by OS` play (later plays target the groups it builds), the `Group GUI-enabled hosts` play, and the Ubuntu GUI-detection `pre_tasks` that decide `gui`. Never pass `ANSIBLE_ARGS` to `verify` - it is forwarded into the localhost-only test playbooks and filters them into no-ops.
- **`ansible.cfg` performance settings:** `gathering = smart` collects facts once per host per run instead of once per play - the 7 plays used to re-run `setup` on every host, and a Windows gather costs 5.4s against 0.7s on Ubuntu. It is safe because every fact this repository reads (`os_family`, `env.HOME`, `user_id`, `distribution*`, `architecture`, `kernel`, `service_mgr`) is constant for the length of a run. `pipelining = True` removes a round trip per task, measured at -37% on Ubuntu; it makes no difference on Windows, where PowerShell start-up dominates, and is compatible with the `sudo_wrapped` become plugin, which inherits sudo's `-H -S -n` and never needs a tty. `callbacks_enabled = profile_tasks` is what makes any of this measurable - reach for its output before optimising anything.
- **Remote-safe tasks:** never use `lookup('env', ...)` for target-host paths (it evaluates on the controller); use `ansible_facts['env']['HOME']` / `ansible_facts['user_id']` instead. Always reach facts through `ansible_facts[...]`, never the injected top-level `ansible_*` aliases: `INJECT_FACTS_AS_VARS` defaulting to true is deprecated and the aliases disappear in ansible-core 2.24, so `ansible_env.HOME` warned on every run. Connection settings (`ansible_become_password`) and magic variables (`ansible_check_mode`) are not facts and keep their names.
- **Vault Usage:** Every secret lives in `inventories/group_vars/all/vault.yml`, the single encrypted file, and that file contains `vault_`-prefixed names only. Roles and playbooks must never reference a `vault_*` name directly - map it onto the real variable in `inventories/hosts.yml` or `inventories/group_vars/all/main.yml`. Never add a second encrypted file and never use inline `!vault` scalars. `ansible.cfg` reads the vault password from `.vault_pass`. A new vault file must also be added to the `.yamllint` ignore list, since yamllint cannot parse ciphertext.
- **Per-host credentials:** named `vault_<host>_username` / `vault_<host>_become_password`, with hyphens in the hostname replaced by underscores (`ubuntu-dev` -> `vault_ubuntu_dev_*`).
- **SSH auth:** the private key comes from `vault_ssh_private_key` via `ansible_private_key` (key *contents*) plus `ssh_agent = auto` under `[connection]` in `ansible.cfg`, which loads it into a per-run ephemeral agent. Never use `ansible_ssh_private_key_file`, never write a key to disk, and never enable `ansible_password`.
- **Privilege escalation:** `become` is intentionally not enabled globally in `ansible.cfg`. Tasks opt in individually - many are deliberately unprivileged because Homebrew refuses to run as root.
- **Never prompt for a password:** every host's sudo password comes from the vault, so no run may stop at a terminal prompt. Tools that shell out to `sudo` themselves need help, because an Ansible run has no terminal: pkg-based Homebrew casks (macOS) get the become password through a throwaway `SUDO_ASKPASS` helper - Homebrew adds `sudo -A` when that variable is set, and it scrubs unknown variables out of the child environment, so the password has to be written into the helper (`no_log: true`, deleted in an `always:` block) rather than passed through `environment:`. Anything that merely needs root, like `mas`, should use `become: true` instead.
- **Tests:** `tests/validate_*.yml` assert on role file contents; update them in the same change when refactoring the asserted roles. `tests/validate_inventory_secrets.yml` additionally asserts that the inventory sources every credential from the vault; its host list is derived from `groups['all']` minus `localhost`, so editing `inventories/hosts.yml` never requires editing the test.
